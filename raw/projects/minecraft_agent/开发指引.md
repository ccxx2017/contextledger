## 一、先把项目重新定义成三个产品

你实际需要开发的不是一个产品，而是三个相互分离的部分。

### 1. 智能体实验平台

负责通用能力：

- 世界与实体；
- 感知；
- 规划；
- 工具；
- 校验；
- 执行；
- 反馈；
- 记忆；
- 技能；
- 多组件协作；
- 日志与证据面板。

这是稳定的技术底座。

### 2. 教学实验框架

负责教学流程：

- 导入课程；
- 提出任务；
- 记录学生预测；
- 设置实验变量；
- 运行基线实验；
- 保存实验结果；
- 显示系统证据；
- 支持修改与重新运行；
- 收集学习证据；
- 判断是否达到课程目标。

这是平台和课程之间的中间层。

### 3. 课程内容包

每节课只是一个配置包，包含：

- 本课标题；
- 学习目标；
- 初始场景；
- 可用传感器；
- 可用工具；
- 安全规则；
- 预设任务；
- 故障条件；
- 引导问题；
- 学习证据；
- 完成条件。

因此，理想结构不是：

```text

第2课场景
第3课场景
……
第30课场景
```

而是：

```text

├─ 通用智能体管线
├─ 通用证据系统
├─ 通用课程运行器

```

## 二、开发时必须固定的四层架构

建议从一开始就把项目划分为以下四层。

### 第一层：领域核心层 Domain Core

只处理AI实验逻辑，不依赖具体UI和动画：

- `WorldState`
- `WorldEntity`
- `Observation`
- `ActionRequest`
- `ValidationResult`
- `ActionResult`
- `MemoryEntry`
- `SkillDefinition`
- `EvidenceEvent`

这一层尽量使用：

- `Resource`
- `RefCounted`
- 类型化数据类；
- 纯函数；
- 可独立测试的服务。

不要把每一种数据都做成Node。Godot官方最佳实践本身也区分了场景、脚本、资源、Autoload和普通数据对象的适用范围；静态类型和警告系统可以在编码阶段发现更多结构性错误。([docs.godotengine.org](https://docs.godotengine.org/en/stable/tutorials/best_practices/index.html?utm_source=openai))

### 第二层：智能体运行层 Agent Runtime

建议采用固定管线：

```text
UserTask
→ WorldSense
→ ContextBuilder
→ BrainProvider
→ ActionParser
→ ActionValidator
→ WorldActions
→ ActionFeedback
→ EvidenceRecorder
```

这一层最重要的原则是：

> **模型、规则大脑和规划器都不能直接修改游戏世界。**

只有`WorldActions`可以改变世界状态。

具体职责如下：

| 组件 | 只负责什么 | 不允许做什么 |
|---|---|---|
| `WorldSense` | 读取允许暴露的世界信息 | 修改世界 |
| `ContextBuilder` | 组装任务、感知和记忆 | 决定动作是否合法 |
| `BrainProvider` | 生成计划或动作请求 | 直接移动角色 |
| `ActionParser` | 解析并规范化结构化消息 | 猜测缺失的危险参数 |
| `ActionValidator` | 校验动作、参数和权限 | 执行动作 |
| `WorldActions` | 执行已批准动作 | 绕过校验器 |
| `ActionFeedback` | 生成成功或失败结果 | 修改历史日志 |
| `EvidenceRecorder` | 保存可观察事件 | 声称展示模型真实思维 |

### 第三层：教学运行层 Pedagogy Runtime

建议建立：

- `LessonRunner`
- `ScenarioLoader`
- `ExperimentController`
- `PredictionRecorder`
- `EvidenceCollector`
- `StudentModificationController`
- `AssessmentTracker`
- `TeacherController`

它们负责把普通智能体模拟变成教学活动。

### 第四层：呈现层 Presentation

包括：

- 2D空间站世界；
- 玩家与智能体动画；
- 学生任务面板；
- 系统证据面板；
- 实验变量面板；
- 教师控制面板；
- 实验记录与导出界面。

呈现层只能通过公开接口和信号读取系统状态，不能越过校验器直接修改核心数据。Godot信号适合让组件对事件作出响应，同时减少彼此的直接引用和耦合。([docs.godotengine.org](https://docs.godotengine.org/en/4.2/tutorials/best_practices/scene_organization.html?utm_source=openai))

## 三、把“系统证据面板”设计成平台中枢

证据面板不是附加UI，而是这个项目最核心的教学功能。

建议所有组件都向统一的`EvidenceBus`发送结构化事件：

```gdscript
class_name EvidenceEvent
extends Resource

@export var event_id: String
@export var run_id: String
@export var correlation_id: String
@export var component: String
@export var event_type: String
@export var summary: String
@export var payload: Dictionary
@export var simulation_time: float
```

一次完整任务应产生类似事件：

```text
TASK_RECEIVED
SENSE_REQUESTED
OBSERVATION_CREATED
PLAN_PROPOSED
ACTION_PARSED
ACTION_VALIDATION_STARTED
ACTION_APPROVED
ACTION_EXECUTION_STARTED
ACTION_SUCCEEDED
WORLD_STATE_CHANGED
TASK_COMPLETED
```

失败时可能出现：

```text
SENSOR_DATA_MISSING
ACTION_SCHEMA_INVALID
ACTION_REJECTED
TARGET_NOT_FOUND
PATH_BLOCKED
TOOL_UNAVAILABLE
HUMAN_CONFIRMATION_REQUIRED
REPLAN_REQUESTED
```

### 面板必须支持三种显示模式

#### 学生简化模式

显示：

```text
AI看到了什么
→ AI提出了什么
→ 安全员是否允许
→ 身体做了什么
→ 最后发生了什么
```

#### 标准实验模式

显示：

- 组件；
- 输入；
- 输出；
- 时间顺序；
- 成功或失败；
- 相关动作；
- 规则命中情况。

#### 教师调试模式

额外显示：

- 完整payload；
- 原始模型输出；
- JSON解析结果；
- 组件耗时；
- 异常堆栈；
- 场景和实体ID；
- 本次运行配置。

三种模式使用同一批事件数据，只是显示深度不同。这样既能适配年龄差异，又不需要维护三套系统。

## 四、先定义四个核心协议，再让编码智能体工作

不要先让编码智能体创建大量节点。先由你亲自确定四个协议。

### 1. 感知协议

```json
{
  "observation_id": "obs_001",
  "observer_id": "agent_01",
  "visible_entities": [
    {
      "entity_id": "oxygen_01",
      "entity_type": "oxygen_tank",
      "position": [320, 180],
      "distance": 126,
      "state": "available"
    }
  ],
  "hazards": [],
  "missing_fields": []
}
```

必须允许故意关闭字段，例如：

- 不提供位置；
- 不提供类型；
- 不提供危险信息；
- 只提供一定距离内的信息；
- 提供过期信息。

这样才能支撑第1～3课以及后续故障实验。

### 2. 动作请求协议

```json
{
  "request_id": "act_001",
  "actor_id": "agent_01",
  "action": "pick_up",
  "arguments": {
    "target_id": "oxygen_01"
  },
  "reason_summary": "任务要求搬运氧气瓶"
}
```

`reason_summary`只是模型或规则系统提供的说明，不应被当成真实内部思维。

### 3. 校验结果协议

```json
{
  "request_id": "act_001",
  "status": "rejected",
  "rule_id": "DISTANCE_LIMIT",
  "reason": "目标距离超过拾取范围",
  "recoverable": true,
  "suggested_next_step": "move_closer"
}
```

建议统一三种结果：

```text
APPROVED
REJECTED
REQUIRES_HUMAN_CONFIRMATION
```

### 4. 执行结果协议

```json
{
  "request_id": "act_001",
  "status": "failed",
  "error_code": "TARGET_MOVED",
  "world_changed": false,
  "recoverable": true
}
```

所有后续记忆、技能、协作和安全课程，都建立在这四个协议上。

## 七、第一个垂直切片应该怎样具体实施

你提出的垂直切片方向正确，建议把它正式定义为：

> **VS-001：安全拾取氧气瓶**

### 场景中只放置

- 一个玩家；
- 一个AI角色；
- 一个氧气瓶；
- 一个障碍；
- 一个目标区域；
- 一个危险区域。

### 只实现一种感知

```text
读取可见物品的ID、类型和位置
```

### 只实现两个工具

```text
move_to(target_position)
pick_up(target_id)
```

### 只实现一条安全规则

```text
AI不得进入危险区域
```

### 只实现一种任务

```text
找到氧气瓶并拾取
```

### 只实现一个证据时间线

```text
收到任务
→ 读取世界
→ 发现氧气瓶
→ 提议移动
→ 通过校验
→ 执行移动
→ 提议拾取
→ 通过校验
→ 执行拾取
→ 任务完成
```

### 必须包含五个失败测试

1. 没有位置传感器；
2. 氧气瓶不存在；
3. 氧气瓶在危险区域；
4. `pick_up`工具没有开放；
5. 动作消息缺少`target_id`。

### 垂直切片验收标准

#### 技术验收

- 规则大脑可离线完成任务；
- 所有动作必须经过Validator；
- 任何组件不能直接绕过`WorldActions`修改世界；
- 每个动作都有唯一`request_id`；
- 成功与失败都产生完整日志；
- 重新运行可恢复初始状态。

#### 教学验收

学生能够回答：

- AI获得了什么信息？
- AI缺少什么信息时会失败？
- 它提出了什么动作？
- 为什么某个动作被拒绝？
- 工具和传感器有什么不同？
- 修改哪个条件能使任务成功？

#### 课堂验收

- 教师能在30秒内重置；
- 能切换正常和故障条件；
- 单次实验控制在1～3分钟；
- 学生不需要打开Godot编辑器才能完成核心实验；
- 错误不会让整个课程停止。

只有这个垂直切片通过三类验收，才继续扩展。

## 八、逐课落实时使用统一的“课程转开发”流程

将来每设计一课，都按照以下七步处理。

### 第一步：填写课程设计卡

每课先回答：

```text
学生要形成什么认识？
学生原本可能有什么错误观念？
必须让学生观察到什么现象？
学生可以改变哪个变量？
需要保存什么证据？
如何判断学生不是猜对，而是真的理解？
```

例如第2课：

```text
核心认识：
人看到的信息不等于AI获得的信息。

错误观念：
屏幕上存在的物品，AI自然就知道。

关键现象：
关闭位置字段后，AI知道有氧气瓶，却不能移动到它。

学生变量：
物品类型、位置、危险区域三个传感器开关。

学习证据：
学生能根据失败日志指出缺少的是位置数据。
```

### 第二步：转换成实验规格

```text
初始状态
自变量
控制变量
观察指标
预期现象
失败分支
重置方式
```

### 第三步：列出平台复用与新增功能

必须分开写：

```text
本课复用：
WorldSense、EvidencePanel、LessonRunner

本课新增：
PositionSensorToggle

禁止为本课专门复制：
Agent、WorldActions、EvidencePanel
```

### 第四步：先写验收测试

例如：

```text
Given 物品类型和位置传感器都开启
When AI执行寻找氧气瓶任务
Then AI能够生成正确目标位置

Given 位置传感器关闭
When AI执行同一任务
Then 系统产生SENSOR_DATA_MISSING事件
And 不产生未经校验的move_to执行
```

### 第五步：拆成编码智能体任务

不要给编码智能体：

> “请完成第2课。”

要给它：

> “根据指定接口新增PositionSensor组件；不得修改WorldSense公共接口；新增两个自动测试；在示例场景加入一个可配置开关；完成后运行测试并报告变更文件。”

每个任务应包含：

- 允许修改的目录；
- 禁止修改的文件；
- 输入文档；
- 接口约束；
- 验收条件；
- 必须运行的测试；
- 输出格式。

### 第六步：技术审查

你检查：

- 是否违反组件边界；
- 是否直接跨层访问；
- 是否硬编码课程内容；
- 是否复制现有逻辑；
- 是否产生不可解释的自动行为；
- 是否新增未记录的Autoload；
- 是否改变公共协议。

### 第七步：教学审查

你亲自扮演学生，检查：

- 学生能否发现目标现象；
- 面板是否提前泄露答案；
- 操作是否比概念本身更难；
- 失败是否有教育意义；
- 是否能重现；
- 是否能形成截图、记录或解释证据。

### `locked`文档的规则

编码智能体：

- 可以读取；
- 不得直接修改；
- 发现冲突时停止；
- 只能提交“建议修改报告”；
- 由你决定是否修改。

### ADR的作用

每个重要架构决定写明：

```text
背景
决定
原因
替代方案
后果
允许修改的条件
```

例如：

> 为什么所有世界修改只能经过WorldActions？

这样几个月后编码智能体不会“为了方便”让Planner直接修改角色位置。

## 十、给编码智能体制定硬性不变量

建议把以下内容写进`08_agent_instructions.md`。

### 架构不变量

1. Brain不得直接访问或修改场景节点；
2. 所有动作必须形成`ActionRequest`；
3. 所有动作必须经过`ActionValidator`；
4. 只有`WorldActions`可以改变模拟世界；
5. 所有关键步骤必须产生`EvidenceEvent`；
6. UI不得成为业务逻辑的唯一存储位置；
7. 课程内容不得硬编码在核心组件中；
8. 在线模型不可用时，核心课程必须可运行；
9. 不得把模型生成的说明称为真实思维过程；
10. 不得在未批准的情况下新增依赖、插件或Autoload。

### 修改不变量

编码智能体每次必须：

```text
读取任务
→ 列出计划
→ 报告预计修改文件
→ 创建或确认分支
→ 实施
→ 运行静态检查
→ 运行测试
→ 启动指定场景
→ 检查运行时错误
→ 截图
→ 汇报差异和遗留问题
```

### 停止条件

遇到以下情况不得自行猜测：

- 设计文档相互冲突；
- 需要改变公共协议；
- 需要新增第三方插件；
- 需要删除大量资源；
- 测试与设计目标冲突；
- 不清楚某个UI究竟是学生端还是教师端；
- 需要处理真实学生数据；
- 需要更改安全不变量。

## 十一、Git工作流要比普通小项目更严格

推荐：

```text
main
├─ develop
├─ feature/VS-001-world-sense
├─ feature/VS-001-action-validator
├─ lesson/L01-scenario
└─ fix/evidence-event-order
```

### 每个编码任务至少有三个检查点

```text
Checkpoint A：开始任务前
Checkpoint B：代码与场景完成后
Checkpoint C：测试与截图验收后
```

### 不要让AI一次同时修改

- 核心协议；
- 场景结构；
- UI；
- 课程内容；
- 测试框架。

一次任务最多集中在一个主要关注点，否则人工审查会非常困难。

### MCP权限建议

- 只开放项目目录；
- 不开放个人目录和无关仓库；
- 默认禁止网络和Shell高危命令；
- 插件版本固定；
- MCP工具清单固定；
- 新工具需要人工确认；
- 每次调用保留日志；
- 不把学生数据、API密钥写入项目或提示上下文。

MCP工具能够形成广泛的数据访问和代码执行路径，因此官方规范强调用户同意、权限边界和人工控制；你的开发环境应按“最小权限”配置。([modelcontextprotocol.io](https://modelcontextprotocol.io/docs/tutorials/security/security_best_practices?utm_source=openai))

## 十二、测试体系应分成四级

### 1. 领域单元测试

测试纯逻辑：

- 感知过滤；
- 参数解析；
- 权限判断；
- 风险分级；
- 记忆过期；
- 技能前置条件。

### 2. 组件集成测试

测试：

```text
Sense → Brain → Parse → Validate → Execute
```

但不必运行完整课程UI。

### 3. 场景验收测试

自动启动测试场景，检查：

- 节点是否存在；
- 信号是否连接；
- 世界是否重置；
- 角色能否执行动作；
- 事件顺序是否正确；
- 是否出现运行时错误。

Godot支持命令行启动项目和调试模式，因此可以把运行检查纳入编码智能体工作流。([docs.godotengine.org](https://docs.godotengine.org/en/4.4/tutorials/editor/command_line_tutorial.html?utm_source=openai))

### 4. 教学验收测试

这一层主要由人完成：

- 学生是否理解；
- 操作负担是否合适；
- 面板是否提供了有效证据；
- 活动是否出现错误暗示；
- 60分钟是否真的装得下；
- 1对1和1对4是否都能实施。

> **自动测试可以证明软件按规则运行，不能证明学生因此学会了。**

## 十三、在线模型与离线规则大脑必须共用接口

建议：

```gdscript
class_name BrainProvider
extends RefCounted

func generate_action(context: AgentContext) -> ActionRequest:
    push_error("Not implemented")
    return null
```

实现：

```text
RuleBrainProvider
ReplayBrainProvider
LLMBrainProvider
StudentBrainProvider
```

### 四种Provider的意义

#### `RuleBrainProvider`

- 离线保障；
- 确定性基线；
- 适合单元测试；
- 便于比较规则与模型。

#### `ReplayBrainProvider`

使用预先保存的模型输出：

- 网络故障时仍可演示；
- 教师可以稳定复现幻觉；
- 避免课堂中的模型输出不可控；
- 适合第7～9课。

#### `LLMBrainProvider`

通过教师代理服务调用模型：

- 不把密钥放入客户端；
- 对输入输出做日志和过滤；
- 对超时、限流和格式错误提供降级。

#### `StudentBrainProvider`

由学生扮演规划员，手动选择或填写动作：

- 支持角色扮演；
- 帮助理解组件职责；
- 不依赖真实模型；
- 适合第10～12课和第22～24课。

## 十四、Blender和美术资产如何进入工作流

你的判断是对的：MVP阶段不要让美术成为瓶颈。

### MVP阶段

使用：

- 色块；
- 简单图标；
- 基础Sprite；
- 统一尺寸碰撞体；
- 明确颜色语义。

例如：

```text
蓝色：玩家
绿色：AI助手
白色：普通物品
黄色：任务目标
红色：危险区域
紫色：记忆或数据对象
```

### Blender的第一批实际用途

等核心垂直切片稳定后，再制作：

- 空间站模块；
- 氧气瓶；
- 能源模块；
- 机器人角色；
- 危险标志；
- 控制台；
- 传感器视觉效果。

如果仍使用2D平台，可以从Blender统一渲染：

- 正交视角Sprite；
- 角色方向图；
- 物品图标；
- 教学动画；
- 分层背景。

### 资产必须带语义元数据

不要让教学逻辑通过文件名猜测物品类型。

错误方式：

```text
if sprite.texture.resource_path.contains("oxygen"):
```

正确方式：

```text
entity_id = "oxygen_01"
entity_type = "oxygen_tank"
tags = ["portable", "life_support", "restricted"]
```

视觉资产可以更换，语义ID和实验行为必须保持稳定。

## 十六、每一课的完成定义

以后不能以“场景运行成功”作为一课开发完成的标准。

建议使用四重Definition of Done。

### 技术完成

- 无阻塞性报错；
- 核心测试通过；
- 可以稳定重置；
- 在线和离线模式至少一种可完整运行；
- 事件日志完整；
- 不违反组件边界。

### 教学完成

- 学习目标可观察；
- 有明确错误观念；
- 有预测活动；
- 有可修改变量；
- 有前后对比；
- 有学习证据；
- 有现实迁移问题。

### 课堂完成

- 60分钟容量经过试讲；
- 1对1可实施；
- 1对4有角色分工；
- 学生操作说明足够清晰；
- 失败后教师能快速恢复；
- 备用活动可在系统故障时使用。

### 安全完成

- 不收集不必要的数据；
- 学生无法越权访问教师功能；
- 在线模型有降级路径；
- 危险操作仅存在于沙盒；
- 日志不暴露API密钥或个人信息；
- AI生成内容有明确身份标识。

## 最后的实施原则

你可以把整个开发方法压缩为下面这条流水线：

```text
课程目标
→ 错误观念
→ 可观察现象
→ 实验变量
→ 平台能力
→ 结构化协议
→ 验收测试
→ 编码智能体实施
→ MCP运行与截图
→ 人工代码审查
→ 教学试验
→ 课程包定稿
```

其中最重要的是三条：

1. **先开发通用实验平台，再制作30个课程包；**
2. **所有智能体行为必须经过结构化协议、校验、执行和证据记录；**
3. **编码智能体负责高速实施，你负责课程正确性、架构决策和最终验收。**

你当前最应该做的下一步，不是开始设计第1课完整教案，也不是让AI一次性建立整个工程，而是先完成以下五份文件：

```text
01_system_architecture.md
02_component_boundaries.md
03_action_and_evidence_protocols.md
04_lesson_package_spec.md
05_VS-001_acceptance_spec.md
```

这五份文件完成后，再让编码智能体创建工程骨架和第一个垂直切片。这样后续逐课落实时，新增的主要是**实验配置、故障条件和学习证据**，而不是每节课重新发明一套智能体系统。
