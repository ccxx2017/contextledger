## 三、现在最需要处理的五个问题

### 1. “oracle 同主链一致”不能裁定上游规格一定有错

这是总结里我最警惕的一处。

如果 oracle 与主链共享解释、规则或辅助函数，两者一致只能证明**实现相互一致**，不能证明业务语义正确。

你需要把八项规格分歧裁定为以下之一：

- gold 错误；
- 实现错误；
- 规格含糊；
- 当前明确不支持。

裁定依据应回到：

> 原始事件、用户意图、预先存在的领域契约，以及各候选解释会造成的行动后果。

不要以“oracle 也这么算”作为最后依据。

同理，`r01` 期望连 oracle 都不满足，**证明存在不一致，但单凭这一点不能证明是哪一方错，更不能直接证明属于“隔离换 precision”。**

建议只做一份简短裁定表，不必再启动大规模架构设计。

### 2. 20 个 BLOCK 必须区分“观察到失败”与“实验本身无效”

可以带着已知产品缺陷做实验，但不能带着失真的测量系统做验收。

建议分类：

| BLOCK 类型 | 处理方式 |
|---|---|
| gold、评分器或事件对齐错误 | 正式验收前修复 |
| 插件没加载、事件漏采、最终输入不可确认 | 正式验收前修复 |
| CL 的真实语义错误 | 可以保留，必须计入结果 |
| readiness 正确阻塞任务 | 计入阻塞及完成率，不能直接算成功 |
| 明确超出支持范围 | 事先声明，单列报告，不事后排除 |

**不要求二十项全部清零，但要求它们不破坏实验的可解释性。**

“已归因”只是起点，不是统一的放行理由。

### 3. `stale_in_host` 命中不等于 Agent 会误用旧状态

旧方案出现在历史里，未必是污染。

例如：

> “不要再使用方案 A，它已被取消。”

这句话包含 A，但它是正确的撤销信息。

因此，建议把观察结果分成三个层次：

1. **旧内容存在**；
2. **旧内容仍被当作有效行动依据供给，或撤销关系表达不清**；
3. **Agent 实际依据旧内容执行了错误动作**。

你们目前四个模拟检查点的证据，应明确落在哪一层。

这还关系到 D1：完整历史天然包含旧状态。如果用“旧字符串是否存在”评分，D1 会被结构性判输，而不是被行为证据判输。

### 4. `verify_preaction.py` 存在，不代表执行关口已经受控

下一轮必须做一次真实宿主集成测试：

```text
根据 revision r 装配
→ 注入取消事件并提交 r+1
→ 尝试执行基于 r 的旧动作
→ 确认工具副作用未发生
→ 宿主重新装配、重新决策
```

验收证据不是“检查脚本返回 fail”，而是：

> **旧动作没有真正执行，而且宿主采取了契约规定的恢复行为。**

OpenCode 官方插件文档列出了 `tool.execute.before`，并给出了通过抛错阻止工具执行的例子；但这只能证明存在可研究的接缝，不能替代你们锁定版本上的实际验证。([opencode.ai](https://opencode.ai/docs/plugins/))

另外，请明确该保证覆盖哪些工具调用，不要将主会话已覆盖扩大表述为所有子 Agent、后台路径都已覆盖。

### 5. 版本钉扎不能只对齐两个版本字符串

建议最小记录：

- 宿主源代码 commit；
- 实际运行文件的路径及 hash；
- 启动命令；
- 插件 commit；
- 依赖锁文件；
- 有效配置及加载的插件清单；
- 模型与调用配置。

OpenCode 官方文档说明，插件可以从全局配置、项目配置及两类插件目录加载，hook 会按顺序运行。因此，仅锁项目插件源码，不足以排除其他已加载插件的影响。([opencode.ai](https://opencode.ai/docs/plugins/))

最重要的验收是：

> 在实际模型请求发送前的可观测边界，证明最终输入确实包含预期装配结果，且没有被后续处理覆盖。

如果只能降级到 `log_tail_adapter_only`，可以继续采集原始轨迹；**不能据此声称已验证最终上下文接管或动作阻断。**

## 四、下一步顺序需要小幅调整

项目 AI 建议：

> 版本钉扎 → 采集 validate_v2 → 影子采集与成对运行。

我建议改为：

> **版本与接缝证明 → 独立 pilot → 修正实验装置 → 冻结 validate_v2 → 正式成对运行。**

区别在于：**不要拿验收集调试插件、评分器和宿主适配。**

### 第一步：只证明实验装置真的工作

用独立的冒烟案例完成：

- 实际插件加载；
- 原始事件完整采集和对齐；
- 最终模型输入可核验；
- lifecycle 从真实抽取链路进入主图；
- 过期动作被实际阻止；
- quarantine 后的 readiness 被宿主实际消费。

未通过时允许继续调试，但不要消耗冻结验收集。

### 第二步：用少量 pilot 跑通成对实验

建议先做两条开发轨迹：

1. 取消 → 晚到工具结果；
2. 改派 → 恢复。

两组分别是：

- **宿主原生上下文机制**；
- **同一宿主 + CL**。

D1/D2 保留为离线诊断基线，但真实接入阶段最重要的问题是：

> 相比这个宿主原本的行为，接入 CL 到底改变了什么？

两组使用相同初始仓库和预设外部事件规则，隔离工作目录、会话及缓存。

**不要要求两组动作发生分歧后仍机械复用同一串工具返回。**例如，一组已经正确取消任务，就不能再假装它发出了另一组的后续调用。应预先定义事件触发条件，保证比较的是同一任务环境，而不是强行相同的内部轨迹。

### 第三步：冻结正式验收集与计分规则

6–8 条真实轨迹适合作为**第一轮小规模价值验证**，不要把它包装成广泛可靠性的证明。

至少包含：

- 取消、改派、晚到、恢复；
- 不应失效的负样本；
- 一个关键事件未裁定或进入 quarantine 的案例；
- 一个能激活新 lifecycle 路径的案例。

如果 `validate_v2` 已被用于修改代码或 gold，应明确转为开发集，再冻结新的验收版本。

### 第四步：报告行动结果，而不只报告状态分数

最小主报告建议只有这些：

| 指标 | 回答的问题 |
|---|---|
| 旧态误用次数 / 有效判断机会数 | 是否减少错误行动 |
| 当前约束违反次数 | 是否制造新的危险 |
| 任务完成数 | 是否仍能完成工作 |
| 无谓阻塞与正确阻塞数 | 是否靠停下来“获得安全” |
| 未裁定事件数量及恢复结果 | 是否把困难问题丢给隔离区 |
| token、延迟、调用成本 | 收益是否值得代价 |

同时保留逐轨迹配对结果，不要只给一个总体均值。

## 五、两项遗留事项的放行意见

### `claim_scope` deferred

可以延期，但必须说明它影响哪些真实案例。

若它恰好决定“取消整个任务”与“只取消某一部分”的区别，就可能直接影响下一阶段取消场景，不能仅因已有注记而默认不阻塞。

### 缺 `effective_at` 不硬隔离

我不反对这一选择。缺时间字段不一定意味着所有事件都无法裁定。

但需要有明确规则：

- 是否存在可信的源版本、因果关联或任务调用标识？
- 如果没有，是否会把“晚收到”误当成“业务上更新”？
- 无法确定时，是否避免自动覆盖关键状态？

**可以不硬隔离，但不能无条件按接收顺序覆盖。**

至于 `turn_090` 的 lint 修复期限：先读取当前实际状态；如果已经到期，应按原契约处理，不要为了进入实验而悄悄顺延。
