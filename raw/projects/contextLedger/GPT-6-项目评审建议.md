# 一、我对项目最核心的评价

## 1. 你真正找到的价值，不是“更好的记忆”，而是“可撤销的任务认知”

普通的记忆问题是：

> 以前说过什么，现在能不能找回来？

ContextLedger 更重要的问题是：

> 哪些先前成立的判断已经不能继续作为行动依据？为什么？受影响的计划和任务有哪些？

这是两个不同的问题。

以一个后台编码 Agent 为例：

1. 原先决定使用方案 A。
2. 子任务按照 A 开始执行。
3. 用户取消 A，改用 B。
4. 基于 A 发出的工具调用晚到返回。
5. Agent 需要决定是否采纳结果、是否继续后续任务。

这里最关键的不是检索命中率，而是**认清返回结果所属的任务版本，并避免旧结果重新取得当前权威地位**。

因此，我建议把项目的内部定位进一步收紧为：

> **ContextLedger 是面向长程 Agent 的、可审计的任务状态裁定与上下文供给层。**

“知识复利平台”可以保留为远期方向，但现在不应影响优先级。MemoryPack 暂缓，是正确选择。

## 2. 最值得保留的，不只是 Graph，而是整套约束

从背景包看，项目最扎实的资产是：

- 原始输入不可改写；
- patch 作为不可变事件；
- graph_state 可重建；
- reconcile 先于正式接受；
- 不确定或失败的写入可以隔离；
- Assembler 按明确契约供给当前态；
- 违规发生后，能够回滚、固定版本并重新恢复审计链。

这条路线与事件溯源的核心思想一致：保留事件历史，通过投影构建当前状态，并用追加的纠正事件而不是改写历史处理变化。它的价值不只是存储结构，而是可追责、可重建和可解释。([learn.microsoft.com](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing))

**因此，不要为了降低 quarantine 比例或提升某次跑分，牺牲这些约束。**

你之前禁止运行中改清洗器、禁止手补 patch 污染主图，是必要纠偏，不是过度洁癖。

## 3. 但“entity_ref + invalidates 稀缺、难复刻”的判断，需要降温

我不建议再把“别人没有失效机制”当作项目成立的前提。

例如，Graphiti/Zep 已有时序知识图谱、事实失效时间以及失效来源追踪的设计。其官方资料明确区分事实在现实中的有效时间和系统获知变化的时间，也记录导致失效的来源事件。**这不证明它比 ContextLedger 更好，但证明这一功能类别不是空白。**([help.getzep.com](https://help.getzep.com/v2/searching-the-graph?utm_source=openai))

所以，你需要证明的差异应该是：

> 在特定长程任务中，ContextLedger 的裁定更可控、错误更可诊断、上下文供给更有契约，而且接入与运行成本合理。

这比“我们使用 Graph，别人使用向量”更有说服力。

# 二、当前最大的风险，不是功能不足，而是保证范围被高估

## 1. “Graph 是唯一权威”应当是运行约定，不是正确性结论

Graph 可以是系统当前接受状态的唯一权威，但不能因为信息进入 Graph，就把它当成客观事实。

建议把这句话正式写进 contracts：

> **Graph 表示系统在给定证据和裁定规则下接受的当前状态，不保证所有记录都与外部世界一致。**

这里至少存在三个层次：

1. **观测**：某个用户、工具或文件提供了什么信息。
2. **裁定**：系统接受了哪些状态变化。
3. **供给**：哪些裁定结果可以作为当前行动依据。

即使暂时不增加新的存储层，也应该保留这三者的语义边界。

尤其要区分：

- “工具声称任务完成”；
- “任务确实完成”；
- “该结果仍属于当前任务版本”。

它们不能被 Extractor 压成同一个无条件的 `Fact`。

## 2. 机械核确定，不等于端到端可靠

你们已经证明的确定性，主要应该表述为：

> 给定固定的已接受 patch 链和执行版本，可以重建同一个状态。

它不自动意味着：

> 对同一段 raw 重新调用 Extractor，会生成同一个 patch。

这两种测试需要分开：

| 测试 | 回答的问题 |
|---|---|
| 固定 patch 重放 | 机械核是否确定、状态是否可重建 |
| 固定 raw 重新抽取 | 语义抽取是否稳定、模型变化是否影响结果 |

Agent 持久化执行的官方实践也强调：非确定性操作应被封装并保存其结果，以便恢复执行时复用，而不是假定重新调用外部服务会得到相同结果。([docs.langchain.com](https://docs.langchain.com/oss/python/langgraph/functional-api?utm_source=openai))

我建议固定记录：

`raw_hash / prompt_hash / model_config / extractor_output / cleaner_version / resolver_version / contract_version / patch_hash`

不要求一次做成复杂平台，但不能只有最终 patch、没有形成它的证据链。

## 3. quarantine 成功，不代表任务状态安全

这是我认为背景包中**最值得立刻补上的判断**。

假设：

- 主图当前认为“允许执行方案 A”；
- 新事件是“取消 A”；
- 这次抽取失败，被 quarantine；
- 主图没有被污染，仍保留“允许执行 A”。

从写入安全看，隔离成功了。

从行动安全看，系统可能继续执行已经被撤销的方案。

所以必须区分：

> **主图未被错误写入**，与 **主图足够完整，可以支持当前行动**。

历史恢复批次约 20.8% 的隔离率，能说明那次隔离机制起效；不能直接说明隔离期间的状态适合继续驱动 Agent。

我的建议是给 Assembler 增加一个最小的状态完整性声明，例如：

```text
state_revision
observed_event_frontier
unresolved_event_ids
readiness: ready | degraded | blocked
reason_codes
```

具体字段名可以调整，关键是：

- 不能把最大成功事件号误当成“之前都已处理”；
- 不能在存在关键未裁定事件时悄悄返回“正常当前态”；
- 对可能涉及取消、改派、授权变化的未处理事件，要有明确的等待、核验或人工升级策略；
- 如果连影响范围都无法判定，应保守扩大阻塞范围，而不是假装无影响。

**quarantine 必须同时有隔离策略、恢复策略和消费策略。**

## 4. 单写者解决写入串行化，不解决全部过期读问题

即便所有 apply 都串行：

1. Agent 根据 revision 100 装配上下文；
2. 新取消事件提交成 revision 101；
3. Agent 仍执行基于 revision 100 生成的动作。

这仍然可能发生。

事件溯源实践中的乐观并发控制，正是通过检查“读状态之后事件流是否改变”来拒绝过期提交，再重新读取和判断。([learn.microsoft.com](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing))

对 ContextLedger，我建议把职责划清：

- CL 提供状态版本和相关前提；
- 宿主在关键动作执行前核验这些前提是否仍成立；
- 变化后重新装配、重新决策。

不用现在实现一个通用事务系统，但需要先在协议里承认这个边界。

同理：

> `must_include` 能保证信息进入最终输入，不能保证模型理解、遵守或执行正确。

真正的硬动作约束，不能只靠上下文注入。

# 三、对当前 lifecycle schema 的裁定：方向支持，但不建议直接全量实施

我赞成你把“同一生命周期拆成多个 entity_ref”的问题提升为一等表达。

但仅根据摘要，我对：

```text
adjudication_key = lifecycle_ref ?? entity_ref
```

的评价是：

> **它可以成为候选冲突检索的分桶依据，但不能独立成为失效裁定依据。**

“属于同一生命周期”不等于“不能同时成立”。

## 1. 必须先区分：生命周期归属与互斥状态槽位

例如，同一个构建任务里可能同时存在：

- 当前执行状态；
- 使用的配置版本；
- 输出文件位置；
- 失败原因；
- 审批结论。

它们可以属于同一个 lifecycle，却不是相互替代关系。

因此，建议先在契约中定义：

> 哪一种状态维度，在什么作用域下，只允许一个当前值？

概念上可以分成：

```text
lifecycle_ref：这些记录属于哪次任务/流程
state_slot：这些记录在描述哪个可替代状态维度
transition_rule：什么变化有资格替代什么旧状态
```

不一定要马上增加名为 `state_slot` 的字段；如果现有类型或 contract 已能表达，可以复用。

**但不能让“扩大冲突桶”悄悄变成“扩大失效范围”。**

## 2. 不要把 entity resolution 的问题搬到 lifecycle resolution

如果 `lifecycle_ref` 仍由 LLM 自由生成，那么原来的风险只是换了字段名：

- 同一流程被写成不同 lifecycle；
- 不同流程被误归入同一 lifecycle。

建议优先级为：

1. 宿主提供的稳定任务、调用、运行标识；
2. 确定性规则可以解析的关联；
3. 显式别名表；
4. LLM 提议的候选关联，经 Resolver 裁定；
5. 无法确认则保留未解析状态，不强行合并。

对于结构化工具事件，尽量不要先转成自然语言，再让 Extractor 重新猜标识。

## 3. `lifecycle_seq` 必须说明“是谁定义的顺序”

至少要区分：

- ledger 接收顺序；
- 业务事件发生顺序；
- 源系统给出的版本顺序。

它们可能不同。

例如，旧工具调用晚到返回，它的 ledger 序号更大，但业务上不应覆盖较新的取消状态。

因此：

- 不建议让 LLM 凭语感生成有权威含义的 seq；
- 不建议把晚到事件自动当作较新状态；
- 缺乏可信顺序时，应进入明确的保守裁定分支。

## 4. 可选字段迁移存在“新旧记录分桶分裂”风险

这是一个很具体的实现检查点。

假设：

- 旧节点只有 `entity_ref=E`；
- 新节点有 `entity_ref=E`，同时新增 `lifecycle_ref=L`。

按照 fallback 规则：

- 旧节点进 E 桶；
- 新节点进 L 桶。

本来应该比较的记录，反而不再相遇。

因此，实施前必须明确选择：

- 派生投影中的确定性归一化；
- 新旧索引桥接；
- 或版本化重建策略。

不能直接修改历史 patch 来“补齐字段”。

## 5. revival 不应抹去中间的失效历史

“方案 A → 方案 B → 恢复方案 A”，不代表第一次 A 从未失效。

我建议把 revival 表达成一次新的恢复事件或新的有效区间；旧事件及其失效依据仍然保留。

如果 MVP 不支持任意历史时间查询，可以明确不支持。**不要通过重新激活旧节点，意外制造“它一直有效”的语义。**

### 我会给这次 schema 实施的放行条件

先写测试，至少覆盖：

- 同 lifecycle 的合法单流推进；
- 同 lifecycle 的不同状态维度共存；
- 不同 lifecycle 不串扰；
- alias 变化但 lifecycle 不变；
- 旧记录无 lifecycle、新记录有 lifecycle；
- 晚到旧事件；
- 重复事件；
- provenance 冲突；
- revival 后历史仍可解释；
- 字段不足时保守失败。

然后再修改实现。

**本轮只承诺解决“有可靠归属、明确状态槽位的单流生命周期推进”。不要顺便承诺解决所有 partial、conditional、provenance 和时序失效。**

# 四、当前评测有进展，但还不能作为可靠性结论

背景包记录：

| 指标 | 改动前 | 候选结果 |
|---|---:|---:|
| Invalidation precision | 0.550 | 0.609 |
| Invalidation recall | 0.579 | 0.737 |
| Active-set Set-F1 | 0.856 | 0.898 |
| Must-include recall | — | 1.000 |

我的解读是：

**方向改善明确；是否足够好，以及是否可泛化，仍未得到证明。**

尤其是，如果 precision 使用通常定义，0.609 意味着该评测中预测为失效的案例仍有相当比例属于误判。它不能直接推成“整体图错误率”，但也不应被包装成可靠裁定已经完成。

下一步评测应补四件事。

## 1. 把分母和隔离样本放回报告

每个指标同时报告：

- TP / FP / FN；
- 轨迹数和案例数；
- 分类型结果；
- 被隔离样本如何计分；
- 提交覆盖率；
- 是否包含真实 Extractor 调用。

我建议同时保留两套视角：

- **已提交部分的裁定质量**；
- **所有输入下的端到端状态质量**。

否则，只要把难例大量隔离，就可能获得好看的 precision，却无法支持实际任务。

## 2. 将开发集与冻结验收集分开

反复用于规则调整、schema 设计的轨迹，应该视为开发集。

建议新增一组独立验收轨迹，并且：

- 按整条轨迹划分，而不是随机拆事件；
- 不把同一个案例的简单改名版当作独立泛化证据；
- 在看结果之前固定判据；
- 验收集一旦用于调参，就转为开发集。

LongMemEval 等公开研究也将知识更新、时间推理和拒答能力作为独立评测维度。这对你的启示不是立即换基准，而是不要让一个综合分数掩盖不同机制的失败。([arxiv.org](https://arxiv.org/abs/2410.10813?utm_source=openai))

## 3. 保留 D1/D2 身份，但把比较条件写清楚

严格保留：

- `D1 = full_history_dump`
- `D2 = exact_surface_last_write_wins`

不要重新命名，也不要改变身份后继续接历史结果。

建议区分两个实验：

1. **完整历史能放入上下文时**：CL 能否以更小输入保留必要信息，减少旧状态干扰？
2. **统一预算受限时**：CL 与预算内基线谁更好？截断策略必须公开。

如果 D1 不受预算限制，就不能一边宣称“同预算胜出”，一边实际上给它完整历史。

另外，`must_include` 的 gold 应独立于 CL 自身生成。否则可能出现“CL 漏掉了约束，同时也没把它放进 must_include 清单”的自我验证。

## 4. 增加一个真正面向行动的主指标

我建议下一轮最重要的新指标不是另一种 Graph-F1，而是：

> **状态发生关键变化后，Agent 仍依据已失效前提采取行动的比例。**

同时观察：

- 当前约束违反率；
- 正确取消或重规划率；
- 任务完成率；
- 无谓阻塞率；
- token、延迟、Extractor 调用成本。

“旧态误用减少，但所有任务都被阻塞”不是成功。

“状态图更漂亮，但 Agent 行为没有改善”也不是成功。

# 五、下一步执行顺序：我建议只推进四个有验收门槛的工作包

## 工作包 A：冻结一个可信基线

**目的：确定我们到底在比较什么。**

交付物：

- 当前仓库 commit、contract 版本；
- 当前 graph_state 与 patch 链摘要；
- lint baseline；
- Extractor、清洗器、Resolver 配置；
- 评测输入、gold、原始计数；
- quarantine 清单及其处理状态；
- 一条可重复运行的重放与评测命令。

**通过条件：**机械重放一致，报告可再生，能够区分历史结果和本次结果。

这不是重开已经封板的 Phase 0，而是为新变更登记比较起点。

## 工作包 B：补齐 lifecycle 契约，再做最小实现

**目的：验证新 schema 解决真实问题，而不是扩大误伤范围。**

顺序：

1. 明确生命周期归属、状态槽位、顺序来源、迁移规则。
2. 先写前述边界测试。
3. 在独立分支实施。
4. 固定版本后重放。
5. 输出新旧结果差异清单，逐项解释新增失效与减少失效。

**通过条件：**

- 修复目标生命周期案例；
- 不破坏无 lifecycle 的旧行为；
- 不出现跨任务、跨状态维度误伤；
- must_include recall 不低于 D1；
- 不靠运行中改规则或手补 patch 获得通过。

不建议现在凭空规定一个“precision 必须达到 0.9”的数字。应该先根据误判代价、覆盖率和具体使用范围确定阈值。

## 工作包 C：让 Assembler 显式声明“这份状态是否适合行动”

**目的：修复 quarantine 后仍可能消费过期状态的缺口。**

最小实现：

- 返回状态版本；
- 返回未裁定事件或完整性风险；
- 返回 `ready/degraded/blocked`；
- must_include 超预算时显式失败，不能悄悄丢弃；
- 给宿主留出动作前版本或前提核验接口。

另外，请检查现有 `apply → lint` 的发布边界：

> apply 是否先生成候选状态，只有本轮新增的阻断性 lint 问题排除后，才正式发布给 Assembler？

如果正式状态先可见、lint 后判失败，那么需要补原子发布或等价隔离。若已经实现，只需把保证写进契约和测试。

## 工作包 D：用一个真实宿主证明行动收益

**目的：从内部机制验证转向实际价值验证。**

不急着覆盖所有 Agent 路径。沿用你的主会话优先策略，但应针对**当前锁定的宿主版本**重新确认装配接缝，不能把背景包中的 `LLM.run(...)` 调查结论直接视为现在仍成立。

我建议首个场景固定为：

> **长程编码任务中的方案取消、任务改派、旧工具结果晚到和任务恢复。**

理由不是“编码 Agent 最热门”，而是这个场景能够同时检验：

- lifecycle 归属；
- 失效裁定；
- 乱序处理；
- quarantine 完整性；
- Assembler 当前态供给；
- 旧状态是否导致错误行动。

先影子模式记录差异；但要记住，**影子模式只能证明可能改变输入，不能证明改变后的行动更好**。后面仍需受控的成对任务运行。

在这个阶段，加入一个真正具有更新/失效能力的外部方案作为对照，比继续只击败 D2 更有意义。

---

# 六、我建议暂时不做的事情

1. **不做 MemoryPack 完整体系。**  
   当前主要风险不是缺软知识，而是状态更新是否可信。

2. **不扩张成通用 Agent 框架。**  
   不把调度、工具执行、权限系统全部收进 CL。

3. **不一次实现全部失效形态。**  
   明确支持范围，比字段看起来全面更重要。

4. **不以降低 quarantine 比例作为独立目标。**  
   应优化的是“有效处理覆盖率、误判风险、恢复成本”，而不是单纯让更多 patch 通过。

5. **不继续无限增加设计文档。**  
   下一轮每项设计都应该对应：失败样本、契约、测试、实现差异、评测结果。

---

# 七、什么结果意味着继续，什么结果意味着收缩

我建议提前写下判据，避免项目进入“总差一个模块”的循环。

### 值得继续扩大投入

- 冻结验收集上保持优势；
- 真实任务中旧态误用明显下降；
- 任务完成率没有被阻塞策略显著拖累；
- quarantine 能被合理恢复或显式降级；
- 收益足以覆盖额外调用、延迟和接入成本；
- 相比具备状态更新能力的方案，存在清晰优势。

### 应该收缩或调整定位

- 只有反复调过的轨迹表现好；
- Graph 指标改善，但行动指标不改善；
- 关键标识仍大量依赖 LLM 猜测，难以建立稳定裁定；
- 通过大量隔离换 precision，却无法处理重要任务；
- 简单的结构化任务状态表加版本校验就已达到相同效果。

最后这一条尤其重要：

**如果证据显示不需要完整 Graph，就应该允许项目退化成更小、更可靠的状态账本。**  
项目的目标是解决状态失效问题，不是证明最初选择的数据结构必须成立。

---

## 最终结论

我对 ContextLedger 的评价是：

> **核心问题选得对，工程纪律已经形成，初步结果支持继续；但可靠性保证和差异化价值仍需要缩小范围、补齐证据。**

下一步最值得集中精力的，不是更多记忆类型，而是三件事：

1. **把 lifecycle 从分桶技巧变成有明确边界的状态转换契约。**
2. **让未裁定事件不能被“干净的旧图”掩盖。**
3. **证明 Agent 因此少做了错误的下一步。**

如果只能给整个下一阶段写一句执行目标，我会写：

> **在一个可复现的长程任务场景里，证明 ContextLedger 能让 Agent 在状态变化后，使用完整、可追溯、未过期的行动依据；无法保证时，明确说明不能保证。**
